# HD2ModManager 总体说明

本文档是 `HD2ModManager` 的开发总纲。后续增加或修改功能时，先修改本文档中的职责、页面和工作流，再实施代码改动。代码实现应服从本文档；如果实现与本文档冲突，应先确认设计是否已经变化。本轮内部 Mod、配置与自动部署改造的阶段顺序、测试门槛和回归场景见 [内部 Mod、配置与自动部署实施计划](内部Mod配置部署实施计划.md)。

## 一、项目定位

`HD2ModManager` 是 Helldivers 2 Mod 的桌面管理器，负责提供用户界面、用户操作流程和任务编排。

管理器本体不负责实现复杂的 patch 解析、patch 写出或游戏资源重建。它通常只调用 `HD2ModCore`；由 Core 编排业务并在需要时委托 `HD2ModAdaptation` 完成游戏资源解析和适配。Manager 把 Core 返回的结果转换为用户可以理解的页面状态、进度和错误提示。

项目目标：

- 管理 Mod 库、配置及唯一活动配置状态。
- 导入、查看、编辑、删除和导出 Mod。
- 检测 Mod 与当前游戏版本的兼容性。
- 调用适配流程修复过时 Mod。
- 为复杂任务提供进度、日志、结果和失败原因。
- 保持便携式目录结构，配置和库数据默认位于程序目录下。

## 二、三层职责边界

### 1. HD2ModManager：界面与流程编排层

Manager 负责 WPF 窗口、主题、布局、页面、ViewModel、命令、导航、选择状态、通知、任务状态，以及调用 Core 服务并展示结果。也可以负责筛选、排序显示、表单校验等纯 UI 逻辑。

Manager 不负责直接解析 patch 二进制结构，不直接读写 Unit、Composite Unit、Material、Texture 或 GPU 资源，不猜测 AssetKey、archive、mesh、section 或 material 映射，也不直接复制旧版 Unit 作为新版输出。

Manager 层的复杂操作统一遵循：

```text
用户操作 -> Manager 构造请求 -> 调用 Core -> Core 按需委托 Adaptation -> 接收进度和结果 -> 更新 UI
```

### 2. HD2ModCore：管理业务与文件业务核心层

Core 负责：

- Mod 库的加载、保存、增删改和索引。
- 配置文件、配置成员关系、顺序和唯一活动配置管理。
- Mod 导入、目录扫描、压缩包处理和存储路径管理。
- 资产标签展示、搜索和资产冲突检测。
- Mod 元数据、封面和备注。
- 配置排序、前置/后置约束、部署、链接、清理和回滚。
- 游戏目录、程序目录和库目录的路径处理。
- archive 索引、资产索引、任务结果、错误码、日志和诊断模型。

Core 不负责具体的 patch 结构重建。需要解析、修改或重新写出游戏资源时，应调用 `HD2ModAdaptation`。

### 3. HD2ModAdaptation：游戏资源适配层

Adaptation 负责：

- 读取当前游戏 Data、默认 Archive 和目标 Archive。
- 读取和写出 patch archive。
- 解析 Unit、Composite Unit、Material、Texture 和 GPU 资源。
- 判断资源版本和 Unit 结构是否可以安全适配。
- 读取模型、mesh、section、material binding 和骨骼信息。
- 使用当前游戏目标资源重建新版 Unit。
- 执行模型转移、骨骼映射、材质和纹理依赖闭包检查。
- 生成当前游戏版本可用的 patch，并执行回读验证。
- 输出适配报告、跳过项、警告和失败诊断。

Adaptation 必须遵守：不能把未适配的旧版 Unit 原样复制到新 patch；当前目标 Unit 是新版输出的结构模板；无法闭合的材质/纹理依赖不得直接传播；输出必须包含必要的目标壳和替换资源。

## 三、Manager UI 总体结构

主窗口由自定义边框窗口构成：

- 顶部为自定义顶栏，包含应用名称、主导航和窗口控制按钮。
- 主内容区域使用灰色背景。
- 内容区域采用双槽位页面容器，支持单页面和左右双页面模式。
- 双页面模式主要用于配置页与 Mod 库并排操作。
- 页面内容使用透明背景。
- 页面内部功能区域使用统一卡片容器。
- 卡片默认高度随内容变化，宽度填充可用区域。
- 页面不自行绘制与主窗口冲突的背景或独立窗口框架。

页面设计优先保证信息可扫描、常用操作距离短、长任务有明确状态、错误可定位到具体 Mod/文件/任务，以及双槽位操作不丢失选择状态。

## 四、页面职责与发展方向

### 1. 主页

主页是应用概览页，不承担复杂编辑操作。当前保留一个占位卡片。后续展示当前配置、Mod 数量、启用状态、最近导入/修复/应用结果、游戏目录和索引摘要，并提供导入、打开库、应用配置等快捷入口。

### 2. 状态页

状态页只用于展示正在执行或最近执行的任务，后续主要保留一个队列卡片，集中显示导入、索引、检测、修复、patch 重建和配置应用任务，以及进度、阶段、成功数、失败数和取消状态。

当前状态页中的资产索引状态卡应移动到设置页。状态页不重复展示静态环境信息。

### 3. 配置页

配置页用于管理当前配置文件及其 Mod 条目。当前包含筛选卡和 Mod 列表卡。

主要功能：选择正在编辑的配置、查看其全部 Mod、添加/移除、调整顺序、设为唯一活动配置、停用活动配置，以及显示冲突和兼容性问题。配置成员身份即启用意图，不再提供条目级启用/禁用。配置页只操作配置关系和活动配置状态，不直接操作 patch 内容。

### 4. Mod 库页

Mod 库页用于管理所有已导入的 Mod。主要功能包括导入、浏览、资产搜索、查看详情、编辑名称/备注/图片、加入配置、删除、打开文件夹、导出、检测过时 Unit、调用 Adaptation 修复以及查看诊断报告。搜索只消费已缓存的名称、备注、资产标签和资产显示信息，并支持常用中英文资产类别同义词；不得因搜索重新扫描 Patch 或 Game Data。

Mod 库页可以发起适配任务，但不实现适配算法。

### 5. 设置页

设置页用于管理运行环境和 Manager 行为，包括游戏目录、Game Data 目录、Mod 库目录、部署模式、导入策略、自动清理、资产元数据更新、资产索引状态和重建入口、日志/诊断目录以及界面行为。

资产索引状态卡从状态页移动到设置页，因为它属于环境配置和维护状态，不属于实时任务队列。

## 五、主要业务工作流

### 1. 导入 Mod

```text
选择目录/压缩包或拖拽文件
  -> Manager 加入导入队列
  -> Core 扫描并导入有效 Mod
  -> Core 保存库和元数据
  -> Core/索引服务刷新派生数据
  -> Manager 更新列表、资产摘要和通知
```

导入失败时保留输入路径、失败阶段、错误消息、部分结果状态和日志/诊断路径。

### 2. 管理配置

```text
用户选择 Mod -> Manager 调用 Core 修改配置 -> Core 校验冲突和排序 -> 保存配置
  -> 若修改的是活动配置则更新部署 revision 并维护缓冲任务 -> Manager 刷新页面与任务状态
```

### 3. 应用配置

```text
用户设为活动配置或修改活动配置
  -> Core 维护 10 秒部署缓冲
  -> 串行部署通道读取最新配置快照
  -> Core 检查并执行清理/部署/验证
  -> Manager 展示任务与结果
```

普通流程不提供绕过队列的手动应用按钮。配置部署不应由 Manager 直接复制文件、创建链接或自行计时。

### 4. 检测与修复过时 Mod

```text
Core/Adaptation 扫描 Mod
  -> 保存明确的 archive、Unit 和 mesh 映射
  -> Manager 展示兼容性结果
  -> 用户选择单项或批量修复
  -> Adaptation 使用当前目标资源重建 patch
  -> Adaptation 回读并生成报告
  -> Core 刷新派生数据
  -> Manager 展示成功、警告、跳过和失败项
```

修复流程不能依赖 UI 层重新猜测资源映射。检测阶段产生的明确映射和 archive 定位必须作为后续修复输入。

### 5. 导出 Mod

导出由 Core 负责文件收集和归档，Manager 负责选择 Mod、输出位置和结果展示。

导出约束：保留原始文件名；压缩包名称使用顶层/根对象名称；压缩包内嵌 manifest；manifest 只保存名称和备注等可移植元数据，不保存资产标签。旧 manifest 的 `tags` 字段允许存在，但导入时忽略。

## 六、数据与状态原则

- Core 的库快照和配置快照是管理业务的权威数据。
- Adaptation 的报告是资源兼容性和修复结果的权威数据。
- 派生数据可以重建，缓存可以删除并重新生成。
- Manager 不把 UI 卡片状态作为业务数据源。
- 任务状态区分排队、运行、成功、警告、失败和取消。
- 长任务不能阻塞 UI 线程。
- 页面刷新应来自服务结果或明确的状态变更。

## 七、内部 Mod、配置与部署链路

### 1. 内部 Mod 库边界

Manager 的内部 Mod 库采用规范化平铺存储：

```text
一个 Mod = 一个内部库目录 = 只扫描该目录顶层 Patch 文件
```

内部 Mod 不依赖外部流通包的 `manifest.json`、选项树或作者声明的互斥关系。内部权威数据是库快照中的 Mod 元数据、顶层 Patch 文件和可重建的派生事实。

外部流通包可以是带 manifest 的树结构、选项型 Mod；未来由独立导入工具拆解成多个平铺内部 Mod。未来导出工具则可将一个或多个内部 Mod 聚合成外部流通包。外部 manifest 不是内部 Mod 的权威元数据来源。

内部 Mod 自动修复时可使用其目录中的 `bak/时间戳/` 保存旧 Patch 文件和内部备份说明；`bak/` 永远不属于活动内容，Patch 扫描、部署、冲突分析和派生缓存必须排除它。

### 2. Mod 事实层

内部事实层必须根据文件重新扫描和验证，不允许由 UI 或 manifest 手工声明技术结论。事实链路为：

```text
Mod 顶层 Patch 组
  -> Patch 组中的 AssetKey
  -> AssetKey 命中的一个或多个原版 Game Data archive / 对象
  -> 当前配置的预计覆盖关系
  -> Data 目录实际部署后的 winner、竞争和异常
```

一个 AssetKey 可以被多个 Game Data archive 共同使用。因此映射必须保留多个目标 Package 与多个可读对象名称，不能强制选择单一“所属对象”。

派生事实至少区分：

- **内容事实**：顶层 Patch 组、文件组成、AssetKey 和解析问题；Mod 内容变化时重建。
- **Game Data 映射事实**：AssetKey 到目标 archive、类型和 Friendly name；Game Data 索引或资产元数据变化时重建。
- **配置预期覆盖事实**：活动配置顺序下的预计覆盖者、winner 和竞争；配置变化时重建。
- **实际部署事实**：Data 中实际 Patch、目标序号、来源 Mod、实际 AssetKey winner 和部署异常；部署、清理或 Data 中受控 Patch 变化时重建。

普通页面不得直接展示 AssetKey、Patch 序号或 archive hash；它们只在高级详情和诊断工具中展示。

### 3. 配置语义

允许存在多个配置，但同一时刻最多只有一个活动配置：

```text
Profiles = 多个
ActiveProfile = 0 或 1 个
```

配置条目不拥有单独的启用/禁用状态：

```text
Mod 在活动配置中 = 已启用
Mod 不在活动配置中 = 未启用
```

因此配置条目只保存 Mod 引用、加载顺序和加入时间。当前测试阶段不迁移旧 `Enabled` 数据；旧本地配置可删除后重新建立。

双槽管理页规则：

```text
左侧配置页 = 当前正在编辑的配置中的全部 Mod
右侧 Mod 库 = 全部内部 Mod - 左侧配置已有 Mod
```

此规则不要求正在编辑的配置一定是活动配置。右侧库为空时，应显示“所有 Mod 都已加入此配置”。单独打开 Mod 库时，仍显示全部 Mod。

### 4. Mod 库位置与自动部署链路

新安装默认将 Mod 库放在游戏目录旁的独立目录：

```text
<SteamLibrary>\steamapps\common\HD2ModManager\mods
```

该目录创建或写入失败时回退到程序目录下的便携式 `mods`。已有自定义库不静默迁移。Manager 不提供复制部署，也不允许用户手工选择链接类型：Mod 库与 Data 同卷且实际硬链接测试通过时使用硬链接；否则测试并使用符号链接。两者均不可用时阻止部署，并提示迁移 Mod 库、打开 Windows 开发者设置或以管理员身份重启。

活动配置发生添加 Mod、移除 Mod、调整顺序、活动 Mod 内容更新或自动修复替换活动 Patch 等变更时，立即请求一次串行部署：

```text
活动配置变更
  -> 标记最新状态需要部署
  -> 取得唯一部署通道
  -> 读取最新配置快照
  -> 根据 Mod 库和 Data 实际能力推导硬链接或符号链接
  -> 无条件清理 Data 中现有受控 Patch 文件
  -> 部署活动配置完整 Patch 集
  -> 写入 activation-state
  -> 重建实际部署覆盖事实
```

即时部署规则：

- 不设置等待时间，不创建可见缓冲任务。
- 同一时刻最多执行一个 Data 写任务。
- 部署运行中产生新变更时只标记一次 dirty；当前提交完成后重新读取最新配置并再部署一次。
- 配置部署通道严格串行；其他导入、索引和分析任务可以并行。
- 非活动配置的编辑只保存，不创建部署缓冲任务。

活动配置切换不需要额外清理阶段：将新配置设为唯一活动配置并立即请求部署。部署任务本身会无条件清理旧 Patch 后完整部署新配置。

停用活动配置是立即操作：取消缓冲/部署任务到安全检查点，删除 Data 顶层所有可识别的 `.patch_n`、`.stream` 和 `.gpu_resources` 文件，删除 `activation-state.json`，并将活动配置设为空。

当前产品假设是 Manager 独占 Data 目录中的 Patch 管理权：游戏本体不使用该类 Patch，其他部署工具和手动放置的 Patch 不受支持，会在重新部署或停用时被清理。游戏运行时允许修改 Data，变更在下次游戏启动时生效。

`activation-state.json` 不作为清理范围的唯一依据，但必须保留用于追溯 Data 中 Patch 的来源、目标序号、部署方式、实际覆盖 winner 和部署异常。

### 5. 普通用户状态与高级诊断

普通 Mod 库、配置页和 Mod 详情页保持简洁。普通详情只显示名称、图像、备注、资产标签卡、当前状态卡和“查看高级详情”入口。

普通状态按用户语义投影为：

- 仅存储。
- 当前配置。
- 已启用。
- 启用但局部覆盖。
- 启用但失效（全部影响均被后续 Mod 覆盖）。
- 文件损坏。
- 过时。
- 状态未知。

Manifest 的作者声明互斥关系不进入内部 Manager。冲突判断分为：

- **archive 级**：用于普通用户提示两个 Mod 都会影响同一个可读对象，表示潜在重叠。
- **AssetKey 级**：相同 `TypeID + FileID` 被多个活动或实际部署 Patch 覆盖时，才是严格的真实竞争；最高有效部署序号是实际 winner。

高级 Mod 详情专供作者和诊断使用，可展示 Patch 组、Patch 内 AssetKey、命中的原版 archive/对象、配置预期覆盖、实际部署 winner、竞争、解析问题、修复和回滚入口。扫描所得技术事实不能直接手工编辑；任何 Patch 修改都必须经过受控重构、模型替换或导入流程，并在完成后重新扫描。

## 八、代码组织规则

- View 只负责布局和交互事件绑定。
- ViewModel 负责页面状态、命令和调用流程。
- Manager Services 负责跨页面的 UI 流程编排。
- Core 负责库、配置、导入、部署和文件管理业务。
- Adaptation 负责游戏资源读取、解析、适配和写出。
- 新增核心功能时，优先在 Core 或 Adaptation 增加服务接口，再由 Manager 接入。
- 不在多个 ViewModel 中重复实现同一业务规则。
- 不在 Code-behind 中实现文件级业务逻辑。
- 所有文件、archive 或资源写出功能必须有失败清理和诊断信息。
- 每个新增 C# 文件应在 using 指令下方添加简短的文件用途注释。

## 九、后续改动流程

1. 先在本文档中修改功能归属、页面位置、输入输出和约束。
2. 判断功能属于 Manager、Core 还是 Adaptation。
3. 为跨层调用确定请求、进度、结果和错误模型。
4. 先实现核心服务，再接入 Manager UI。
5. 为成功、失败、取消和重复执行补充测试。
6. 完成后同步更新本文档中的当前状态。

功能归属的默认判断：只影响显示和交互的功能属于 Manager；影响 Mod 库、配置、文件部署或索引的功能属于 Core；影响 patch、Unit、Material、Texture、GPU 或游戏 Data 的功能属于 Adaptation。
